# ADR-013: Keep host specifics in adapters around a host-neutral core, ship a generic Claude Code plugin, and generate the memory skill per member

**Status:** proposed
**Date:** 2026-10-22

## Context

The core must not depend on any host (U5), a second adapter must need no core
change, Claude Code gets hooks while the other hosts get none (C7), every host
reaches the server as a remote MCP connector (U1), and the memory skill's
description is generated from the schemas of the member's stores (C5c), so it
cannot be a static file. Members install nothing but what their host offers
(U4); a developer installs the Claude Code adapter in one command (U2).

## Decision

- **Packages and dependency rule**, in one Python package `tiroir`, enforced
  by `import-linter` contracts in CI (ADR-002):
  - `tiroir.core`: schema, store, Git, index, retrieval, embeddings, detection,
    context, links, proposals, purge, migration, evaluation, members and
    access. Imports no other `tiroir` sub-package and nothing host-specific
    (U5).
  - `tiroir.server`: the HTTP application: MCP endpoint, OAuth (ADR-015),
    account and administration pages, Git endpoint, health (contract
    `http-routes.md`). Imports `tiroir.core` only.
  - `tiroir.cli`: the member CLI (an MCP client of a server) and the
    administration CLI (`tiroir admin …`, run in the container, calling
    `tiroir.core` directly). Never imports `tiroir.server` or an adapter.
  - `tiroir.adapters.<host>`: what a host needs beyond MCP, such as the
    rendering of the context block for hooks; imports `tiroir.core` only.
  The Claude Code plugin itself is a directory of declarative files in this
  repository (`plugins/claude-code/`), not Python.
- **Claude Code adapter:** a plugin published in a marketplace hosted by this
  repository, installed with one `claude plugin install` command (U2). Its
  manifest:
  - asks once, through `userConfig`, for the server's address;
  - declares the tiroir MCP server (`type: http`, `url:
    ${user_config.server_url}/mcp`); Claude Code runs the OAuth sign-in on
    first use (ADR-015);
  - declares the `UserPromptSubmit` hook of type `mcp_tool`, calling
    `tiroir_context` on that server with the prompt, working directory and
    session id, timeout 2 s (ADR-009, contract `claude-code-hook.md`);
  - ships the static init skill.
- **Claude Desktop, web and mobile:** the member adds a custom connector with
  the server's address and signs in (U4); no adapter. The init skill is
  published as a skill archive with each release.
- **The memory skill:** generated by the core per member, from the schemas of
  the stores they are granted: a description of at most 150 tokens in the
  stores' memory language naming the drawer types and shared-space topics
  (C5, C5c), and a body explaining the tools, scoping, confirmation and
  audience rules, and when to write: a log entry for each new fact,
  decision, deadline or document about a drawer, a summary proposal when a
  durable fact changes, nothing for chatter (W7). It never names a store the member cannot reach (X1a). The
  member downloads it as a skill archive from their account page, which
  states when it is out of date (after a migration or an access change); the
  `tiroir_status` tool says so too. Uploading it is one documented step in
  each host.
- **MCP server instructions:** one sentence pointing to the memory skill, to
  keep the fixed per-session cost within C5.

## Alternatives considered

- **A local `tiroir` binary run by Claude Code** (the local-first design) -
  needs an install on every developer machine; the plugin and MCP reach the
  server directly.
- **A per-server plugin marketplace served by tiroir** - the address could be
  built in, but Claude Code would need credentials to fetch it, and each
  server would publish its own copy of the plugin; one generic plugin asking
  for the address is simpler.
- **A static, generic memory skill** - no generation step, but a description
  that does not name the member's own drawer types triggers far less reliably,
  which is what C5c is for.
- **Skill content served through MCP prompts or resources** - no upload, but
  the member must pick them by hand each time; skills trigger by themselves.
- **Enforcing the dependency rule by separate distributions** (one package per
  layer) - stronger isolation, but versioning and release work for one
  product; `import-linter` fails the build on a forbidden import.

## Consequences

A second host means a new adapter plus, if it has hooks, a mapping of its
events onto `tiroir_context`. Each host has one manual step for the memory
skill until hosts can fetch skills from a connector; the skill can go stale,
which the account page and `tiroir_status` report. The plugin depends on
Claude Code's `mcp_tool` hooks and plugin `userConfig`, which the first
milestone verifies with the supported Claude Code version.
