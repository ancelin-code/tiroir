# ADR-013: Keep host specifics in adapters around a host-neutral core, and generate the memory skill per machine

**Status:** proposed
**Date:** 2026-10-21

## Context

The core must not depend on any host (U5), a second adapter must need no core
change (brief §12), Claude Code gets hooks while Claude Desktop gets none (C7),
and the memory skill's description is generated from the schemas of the stores
in use (C5c), so it cannot be a static file shipped in a package.

## Decision

- **Crates and dependency rule**, one Cargo workspace, enforced by the
  compiler since a crate can only use what it declares as a dependency:
  - `tiroir-core`: configuration, schema, store, index, retrieval, detection,
    context, proposals, sync, purge, migration, evaluation. Depends on no
    other tiroir crate and on no host-specific code (U5).
  - `tiroir-mcp`, `tiroir-cli`: surfaces over the core; they never depend on an
    adapter crate.
  - `tiroir-adapter-<host>`: one crate per host, depending on the core only.
  - `tiroir`: the binary, wiring the CLI, the MCP server and the adapters
    together (ADR-002).
- **Adapter interface:** an adapter provides `install`, `uninstall` and
  `status` (each with a dry run that prints the planned changes), and
  translates host events into calls on the core's context API and back
  (contract `context.md`). An adapter never reads the store or the index
  directly.
- **Claude Code adapter:** a Claude Code plugin published from this repository
  (marketplace entry), declaring the MCP server (`tiroir mcp`), the
  `UserPromptSubmit` hook (`tiroir hook claude-code user-prompt-submit`, 2 s
  timeout) and the static init skill. Both commands run the installed
  `tiroir` binary (ADR-002). `tiroir install claude-code` checks that the
  binary is on the path, installs or checks the plugin, and writes the
  generated memory skill.
- **Claude Desktop:** no adapter in the hook sense. The `.mcpb` bundle
  (ADR-002) installs the MCP server. The init skill is published as a skill
  archive with each release; the memory skill archive is generated after init
  and after every schema change. The install guide tells the user where to add
  them in Claude Desktop's settings, one documented step each.
- **The memory skill:** generated by the core from the stores in use: a
  description of at most 150 tokens in the stores' memory language naming the
  drawer types and shared-space topics (C5, C5c), and a body explaining the
  tools, scoping, confirmation and audience rules. Regenerated after
  `store connect`, `store remove`, init and every migration; adapters only
  decide where the file goes.
- **MCP server instructions:** one sentence pointing to the memory skill, to
  keep the fixed per-session cost within C5.

## Alternatives considered

- **Hooks and host config written by the core** - simpler at first, but every
  new host then changes the core, which §12 forbids.
- **A static, generic memory skill** - no generation step, but a description
  that does not name the user's own drawer types triggers far less reliably,
  which is what C5c is for.
- **MCP prompts instead of skills on Claude Desktop** - available without
  upload, but the user must pick them by hand each time; skills trigger by
  themselves.

## Consequences

A second host means a new adapter package plus, if it has hooks, a mapping of
its events onto the same context API. The Claude Desktop path has one manual
step (adding the skill archives) until Desktop can install skills from a
bundle; the init skill can tell the user exactly where to click. Regenerating
the skill on every schema change is one more step that `doctor` checks.
