# Custom Schema

By default, a tiroir store is organised like the bundled `accounting-firm`
example: one drawer per client. If your team works differently, you describe
your own organisation in a file, the **schema**, and tiroir does the rest. This
page takes you from nothing to a working store with your own drawers. Count
about 30 minutes for a first try.

!!! note "No guided setup in 0.1.0"

    You write the schema by hand, on the server. A guided *init*, where Claude
    interviews a member in their language and proposes the schema, is planned
    for a later milestone and does not exist yet. Until then, a custom schema
    is a **preset** of your own: a folder on the server that a store is
    created from.

## The ideas in five minutes

tiroir organises memory the way people organise paper files, and keeps it as
plain Markdown files in a Git repository.

| Term | What it is | Example |
|---|---|---|
| **Store** | One memory, one Git repository. A personal store belongs to one member; a team store is shared by the members you grant. | `my-team-memory` |
| **Drawer** | One "thing" your memory is about: one client, one code repository, one engagement. A drawer is a folder. | the drawer of the `billing-api` repository |
| **Drawer type** | The kind of a drawer. All the drawers of a type are organised the same way. | `repo`, `client` |
| **Summary** | The drawer's current state: a short document of named sections, rewritten as things change. | what `billing-api` is for, its architecture |
| **Log** | The drawer's history: one small dated file per event, never edited afterwards. | "2026-10-21: migrated invoices to the new table" |
| **Shared space** | Documents that belong to no drawer: conventions, procedures, calendars. | `shared/conventions.md` |
| **Schema** | The file `tiroir.yaml` that declares the drawer types and how each one is organised. | this page |
| **Preset** | A folder holding a schema, its templates, shared documents and, optionally, starting drawers. | `my-team` |

A store with one drawer looks like this on disk:

```text
my-team-memory/
  tiroir.yaml                  the schema
  MEMORY.md                    the table of contents, generated by tiroir
  templates/                   what a new summary or log entry looks like
  shared/conventions.md        a shared document
  repos/billing-api/           one drawer
    summary.md                 its summary
    log/2026/10/…md            its log, one file per entry
```

Two rules of thumb will guide every choice below:

- **What is true now goes in the summary; what happened goes in the log.** "The
  service runs on PostgreSQL" is a summary fact. "We moved to PostgreSQL on
  21 October" is a log entry.
- **A drawer is something people name in conversation.** If your team says "have
  you seen the Dupont file?" or "what about billing-api?", then clients or
  repositories are your drawers.

## Before you write anything: three questions

Take a sheet of paper and answer:

1. **What are your drawers?** The things your team keeps coming back to:
   clients, repositories, projects, patients, suppliers. Start with one type.
2. **What do you want to remember about each one?** List the headings of the
   summary, in the order you would read them. Four to six is plenty. These
   become the summary *sections*.
3. **What identifies a drawer?** A code, a name, a slug. This becomes the
   drawer's *fields*, and its folder name.

The rest of the page builds a store for a team that wants one drawer per code
repository. Replace "repository" with your own answer as you go.

## Step 1: Prepare the presets folder

The bundled presets live inside the container image. Mounting your own folder
over them would hide them, so copy them out first. From the directory that holds
`compose.yaml`, with the stack running:

```sh
docker compose cp tiroir:/app/presets ./presets
mkdir -p presets/my-team/templates presets/my-team/shared
```

`presets/accounting-firm` is now yours to read: it is a complete example of
every file below. `my-team` is the name you will give to `--preset`: lowercase
letters, digits and hyphens, starting with a letter or a digit.

Now tell Compose to use this folder. Create `compose.override.yaml` next to
`compose.yaml`; Compose reads it automatically:

```yaml
services:
  tiroir:
    volumes:
      - ./presets:/app/presets:ro
```

```sh
docker compose up -d
```

From now on, a change to a file under `presets/` is seen by the server at once;
no restart is needed.

## Step 2: Write the schema

Create `presets/my-team/tiroir.yaml`:

```yaml
tiroir: 1

store:
  id: 4b7e2c1a-9d3f-4e8b-a1c2-5f6d7e8f9a0b
  name: my-team
  audience: team
  language: en
  description: "What our team knows about its repositories."

shared:
  topics: [conventions, release process]

drawer_types:
  repo:
    label: Repository
    label_plural: Repositories
    description: "One code repository of the team."
    path: "repos/{name}"
    fields:
      name:
        type: text
        required: true
        pattern: "[a-z0-9-]+"
        description: "The repository's name, in lowercase, such as billing-api."
      aliases:
        type: list
        description: "Other names people use for it."
      language:
        type: enum
        values: [python, typescript, go, other]
        description: "The main language."
    summary:
      template: templates/repo-summary.md
      sections: [Purpose, Architecture, Conventions, Open questions]
    log:
      template: templates/repo-log.md
    detect:
      names: [name, aliases]
    inject:
      sections: [Purpose, Conventions]
      max_tokens: 800
```

Read it from the top:

- **`tiroir: 1`** is the version of the file format. Always `1`.
- **`store`** describes the store. Leave it as it is: when you create a store,
  tiroir generates its identity and replaces `id`, `name`, `audience` and
  `language` with the values you give on the command line. They must be present
  and valid, nothing more.
- **`shared.topics`** says what the shared space is about. It is a hint for
  Claude, not a list of files.
- **`drawer_types`** is the heart of the file: one entry per kind of drawer,
  here `repo`. The key (`repo`) is the type's name.
    - **`label`, `label_plural`, `description`** are the words used when tiroir
      talks about the type. Write them in the store's language.
    - **`path`** says where a drawer lives. `repos/{name}` means that the
      drawer of a repository whose `name` is `billing-api` is the folder
      `repos/billing-api`. The placeholder must be a **required** field, and it
      is what makes each drawer unique.
    - **`fields`** is the drawer's identity card, the information that is not
      prose. Each field has a `type`: `text`, `number`, `date` (`2026-10-21`),
      `boolean`, `enum` (one of the `values` you list) or `list` (a list of
      text). `required: true` makes it mandatory, and `pattern` restricts a
      `text` field to a regular expression.
    - **`summary`** names the template of a new summary and its **sections**,
      the level-2 headings, in order. They are the units that tiroir finds,
      reads and, later, merges.
    - **`log`** names the template of a new log entry. Optional.
    - **`detect.names`** lists the fields whose values designate the drawer in a
      conversation. Optional. Most of what uses it arrives with the retrieval
      milestone, so in 0.1.0 you can leave it out or fill it in now.
    - **`inject.sections`** and **`max_tokens`** say which sections are put
      before Claude when the drawer comes up, and how much. Optional, with the
      same remark.

Then the two templates. A summary template holds exactly the sections you
declared, in the same order, with a line of guidance under each. Create
`presets/my-team/templates/repo-summary.md`:

```markdown
# {name}

## Purpose

What this repository does, and for whom.

## Architecture

The main parts and how they fit together.

## Conventions

What to know before changing the code.

## Open questions

What is still undecided.
```

`{name}` is replaced by the drawer's field of that name when it is created. The
log template is the shape of a new entry. Create
`presets/my-team/templates/repo-log.md`:

```markdown
**What happened:** one sentence.

**Next step:** who does what, and by when.
```

Finally a shared document, `presets/my-team/shared/conventions.md`. Claude reads
it the first time it uses the store in a session, so put in it what you want
every entry to respect:

```markdown
---
title: Team conventions
---
# Team conventions

## Writing

Write in English, in short sentences.

## Secrets

Never write a password or a token in memory.
```

## Step 3: Give it a first drawer

In 0.1.0, members can search, read and add log entries, but they cannot create
a drawer or rewrite a summary from Claude. The drawers must therefore exist when
the store is created: you put them in a `data/` folder of the preset, laid out
exactly as in the store. Create
`presets/my-team/data/repos/billing-api/summary.md`:

```markdown
---
type: repo
name: billing-api
aliases: [billing, invoices-api]
language: python
---
# billing-api

## Purpose

Issues invoices and records payments for the web shop.

## Architecture

A FastAPI service in front of a PostgreSQL database.

## Conventions

Every change needs a migration and a test.

## Open questions

Do we keep the legacy CSV export?
```

The top block, between the two `---` lines, holds the drawer's fields: `type` is
the name of the drawer type, and the others are the fields you declared. Then
come the sections, with exactly the headings of the schema. Add one folder like
this per drawer. Start with one or two drawers: 0.1.0 has no way to add drawers to a store
once it is created, so put in `data/` every drawer you want at the start.

!!! warning "Keep to the schema"

    In 0.1.0, tiroir checks `tiroir.yaml` when it creates a store, but it does
    not check the drawers of `data/`: a misspelled section or a value that is
    not in an `enum` goes through. Copy the template headings exactly.

## Step 4: Create the store

Try it on a machine that does not matter first, for example your laptop with the
same `compose.yaml`: 0.1.0 has no command to delete a store, so a store you
created by mistake stays there.

```sh
docker compose exec tiroir tiroir admin stores add my-team-memory \
  --audience team --language en --preset my-team
```

The command prints `store: my-team-memory`. A team store has no member yet: give
access to the members you created (see the
[Installation Guide](../install/vps.md#5-create-a-member)).

```sh
docker compose exec tiroir tiroir admin grant alice my-team-memory write
docker compose exec tiroir tiroir admin grant bob my-team-memory read
docker compose exec tiroir tiroir admin stores list
```

If the schema is wrong, nothing is created, and every problem is listed with its
location:

```text
error: schema.invalid: the schema has 1 violation:
schema.invalid: drawer_types.repo.fields.language.type (line 35): expected one of: text, number, date, boolean, enum, list
```

The key path (`drawer_types.repo.fields.language.type`) and the line say where
to look. Fix the file and run the command again.

| Message | Meaning |
|---|---|
| `schema.invalid` | A key is unknown, misspelled, mis-indented or of the wrong type. An unknown key is always an error, so that a typo never silently disables a rule. |
| `preset.unknown` | There is no folder of that name in `presets/`, or the name has capitals or spaces. |
| `store.exists` | A store with that name exists already. |

## Step 5: Look at the result

The store is a Git repository inside the container, in a folder named by an id,
not by the store's name. Find yours by its title:

```sh
docker compose exec tiroir sh -c '
  for repo in /data/stores/*.git; do
    echo "$repo: $(git --git-dir="$repo" show main:MEMORY.md | head -1)"
  done'
```

```text
/data/stores/6f0c5a3e-….git: # my-team-memory
```

Then print the table of contents that tiroir generated, `MEMORY.md`, and the
list of files, with the folder you found:

```sh
docker compose exec tiroir git --git-dir=/data/stores/<id>.git show main:MEMORY.md
docker compose exec tiroir git --git-dir=/data/stores/<id>.git ls-tree -r --name-only main
```

`MEMORY.md` looks like this:

```text
# my-team-memory

What our team knows about its repositories.

Each drawer is a folder holding `summary.md`, its summary, and `log/`, its dated log entries. Shared documents are under `shared/`.

## Repositories

- [[repos/billing-api/summary]] — Repository: billing-api, billing, invoices-api
```

Then connect as `alice` with [Claude Desktop](../connect/claude-desktop.md) and
try, in that order:

> Which drawers do I have in my-team-memory?
>
> Show me the summary of billing-api.
>
> Add a log entry to billing-api: "Moved the invoice export to a nightly job."

Claude should list the drawer, read its summary and writes the entry as a new dated
file under `repos/billing-api/log/`. If all three work, your schema works.

## Going further

- **A second drawer type.** Add another entry under `drawer_types` (`project`,
  `incident`), with its own `path`, fields, templates and sections. Two types
  must not use overlapping paths: `repos/{name}` and `repos/{name}/docs` would
  clash.
- **A different language.** `language` is the memory language, for example `fr`.
  Write the labels, the section headings and the templates in that language;
  `--language` on `stores add` overrides the one in the file.
- **Learn from a complete example.** `presets/accounting-firm` is the full
  version of what you built: a French schema with six fields, six sections,
  templates, shared procedures and 23 drawers with their logs.
- **Every key, every rule.** The
  [schema contract](https://github.com/ancelin-code/tiroir/blob/develop/delivery/contracts/schema.md)
  lists them all, with the exact error for each.

## Good to know

- **A preset is a starting point.** It is copied when the store is created.
  Changing the preset afterwards does not change the stores already made from
  it, and 0.1.0 has no command to change the schema of an existing store; schema
  migrations are planned. Settle the schema on a test store before the real one.
- **Upgrades.** With `./presets` mounted, the presets of a new image no longer
  appear. Copy them out again if you want them.

See the [CLI Reference](../reference/cli.md) for `stores add` and `grant`, and
the [Installation Guide](../install/vps.md) for the stack.
